# クレジットカード決済 受け入れ条件

本書は`requirements.md`を根拠とする。各条件は**実装の現状ではなく、承認済み業務仕様**から作成。具体的なDB列名・API契約はソース確認後に補完する。

| AC ID | 要件ID | 検証可能な受け入れ条件 |
|---|---|---|
| AC-CC-001 | 001,009 | 締め時点の支払方法・締区分が条件を満たし、決済時点のカード有効性が有効で、金額が下限以上の請求のみ選択・実行可能 |
| AC-CC-002 | 002 | 決済APIに渡す金額が今回請求額と一致し、部分金額指定は不可 |
| AC-CC-003 | 003 | API成功後にDB保存失敗を注入しても同一請求の再決済API呼出しを行わず、管理者対応が必要となる |
| AC-CC-004 | 004,010 | タイムアウト・通信断・応答不明後、管理者復旧前の再決済API呼出し回数は0 |
| AC-CC-005 | 005 | 決済成功かつエラーなしの取引のみ全額取消APIを呼び出せる |
| AC-CC-006 | 006 | 決済済み請求は取消と整合性確認が終わるまで修正・削除・締め直し不可 |
| AC-CC-007 | 007,013,031 | カード削除後も履歴照会と取引番号を用いた取消が可能 |
| AC-CC-008 | 008 | 決済日がDなら入金日はD+1暦日（週末・月末・年末も同様） |
| AC-CC-009 | 011 | 同一請求への同時リクエストで決済APIに進めるのは最大1件 |
| AC-CC-010 | 012,018 | 取消後は元の請求番号で再決済できず、最新マスタ情報で締め直した新番号のみ再決済可能 |
| AC-CC-011 | 015 | 明確な失敗を返した請求のみエラーとして記録し、後続の請求を処理 |
| AC-CC-012 | 017 | 取消成功後は対象入金明細が削除され、決済と取消の両履歴が残る |
| AC-CC-013 | 019 | 集計に有効成功取引のみ含まれ、取消済み・エラーは含まれない |
| AC-CC-014 | 021 | 取消結果不明を記録し、管理者復旧前は再取消・再決済・請求変更API/更新を実行しない |
| AC-CC-015 | 022 | TPとFRの対象請求データは独立し、誤った相互参照・処理をしない |
| AC-CC-016 | 023 | 権限のないユーザーは画面・直接操作経路の双方で保護対象操作を実行できない |
| AC-CC-017 | 024 | 下限未満、0、負数は決済API呼出し0回。下限値ちょうどは他条件が満たされれば許可 |
| AC-CC-018 | 025 | 手数料表示は表示時点の最新料率で計算される |
| AC-CC-019 | 026 | 決済成功・失敗・取消の履歴、および照会・復旧の操作ログを所定の別経路で確認できる |
| AC-CC-020 | 027 | 一括決済中の結果不明請求をロックしつつ後続請求を続行 |
| AC-CC-021 | 028 | 専用管理者権限がないユーザーは結果不明状態を解除できない |
| AC-CC-022 | 030 | 明確な失敗と結果不明が画面上で識別可能 |
| AC-CC-023 | 032 | 取消後に入金明細が残存していても締め直し処理自体は拒否されない。データ不整合はリスクとして別記 |

## 未確定・保留
- REQ-CC-014/020: 強制終了後の検知・復旧方式は未定。実装方式の合否を決めない。
- REQ-CC-016/033: 取消API成功後のDB更新失敗に対する具体的復旧方式は未定。
- REQ-CC-029はREQ-CC-032へ統合済み。
- 取引結果不明の永続化方式、管理者操作UI、ログの項目/保存期間、権限コード、料率取得失敗時の扱いは実装確認・追加仕様確認が必要。

## 合否判定
`PASS`（期待結果を確認）/ `FAIL`（期待結果と不一致）/ `BLOCKED_ENV`（環境制約）/ `BLOCKED_SPEC`（仕様未定）/ `NOT_RUN`（未実施）。静的コード確認のみの場合は`REVIEW_ONLY`とし実行テスト合格とは区別する。
