## 隔離構成とソフトウェア

1. Windows VMにVisual StudioまたはMSBuild（.NETデスクトップビルド）、.NET Framework 4.7.1ターゲティングパックと互換ランタイム、NuGetを用意する。`EmuLunch2.csproj` の構成に合わせてDebug x86からビルドし、SPREAD for Windows Forms/FarPoint 10.0.4009.2012、ActiveReports v11 11.0.9393.1、PluginInputMan、および参照されるOffice／Excel／VBIDE COMを適合バージョンで解決する。ベンダー提供の配布・ライセンス条件を確認する。フォームのE2Eは対話デスクトップ、並行ケースは同一VMの別プロセスか同じ隔離ネットワークの2 VMを使用する。
2. 既存 `EmuLunch2/packages.config` を復元する。DotNetZip 1.16.0、log4net 3.2.0、Newtonsoft.Json 13.0.4、WindowsAPICodePack-Core 1.1.2／Shell 1.1.1。まず依存取得・ビルドを完了し、その後VMの外向き通信を既定拒否に切り替える。アダプターテストには.NET 8 SDK、HTTPスタブには組込みKestrelを使う.NET 8コンソール／Webプロジェクトを想定。UI自動化が必要な場合のみ FlaUI.UIA3 の導入を検証する。SQL管理は `sqlcmd` またはSSMS。
3. VM内または隔離ネットワーク内に専用SQL Server Developerを用意する。SQL Serverのバージョン・互換性レベル・照合順序は、承認された**スキーマのみ**の提供元に合わせる。リポジトリ内の `SQL/` は業務クエリも含むため、DB全体を復元できる初期化資材として扱わない。起動・ログイン・締め処理に必要なビュー、関数、トリガー、列、制約、権限マスタまで照合し、スキーマが得られなければ該当ケースのBLOCKED_ENVを維持する。ランごとのDBを作成し、シード／障害注入用とアプリ用の権限を分ける。
4. `DBUtil.ConnectionString → ConnectionInformation.Get` の実装に沿い、実行用コピーの `EmuLunch2.exe.config` にローカル生成した `DataSource`、`InitialCatalog`、`UserID`、暗号化形式の `Password`・`CompanyCD`、合成 `FRApiKey` を設定する。CompanyCDとPasswordは既存の復号形式に適合させる。設定ファイル、暗号化済みの値、SQL認証情報、DBダンプはGit管理外の作業領域に保管する。コミットは値を含まないひな形と合成データ生成コードに限る。
5. `WebAPIBase._urlFR` はApp.configのURLからでなく、隔離DBの `システム設定` の「FR決済用中間サーバWebAPIURL」から初期化される。必要なシステム設定はテスト用に用意し、利用する外部サービスの接続先は全てスタブに向けるか遮断する。設定を書き換えたらプロセスを再起動する。OS側でテストSQLとHTTPスタブへの通信のみを許可し、VPN・プロキシ経由の外部経路を閉じる。
6. 起動前に、隔離DB識別子・サーバー・企業CD・スタブ起動状態・接続先許可規則を照合。テスト用合成ユーザーでログインし、照会1件とスタブへの疎通を確認する。フォームが別DB・別URLを参照する、必要な資材が欠ける、または外部遮断を証明できない場合は業務テストを開始しない。

API成功後DB失敗は、テストDB内の対象行に限定したテストトリガー等で、履歴INSERT、請求UPDATE、入金INSERT／DELETEの各段階を個別に失敗させる。事前に独立接続で注入条件を確認し、終了時にテストDBごと破棄する。SQLエラーを起こす方法を一律にコミット障害と扱わず、コミット相当の接続喪失を扱う場合は実際の失敗位置とコミット済みの有無を独立接続で記録する。DB全体をテスト側の1トランザクションに包むと多接続の実挙動を変えるため、ケース単位で初期化する。

## FR HTTPスタブと優先実行順

- `sale/settlement`、`sale/cancel`、`info/getSettlement`、`info/getFeeRateList`、`info/deleteCard` を `FRSettlement.cs` の要求・応答モデルに沿って実装。成功のヘッダー／業務結果、ヘッダーでの明示失敗、ヘッダー成功・業務失敗を別シナリオにする。照会応答は合成の取引番号、請求番号、結果を整合させ、照会不可も独立に指定する。未知のルート・シナリオは失敗として記録する。
- 通信断は要求を受信し、合成台帳に成功を残してから応答前に切断するケースと、処理前に切断するケースを分ける。タイムアウトは応答を製品の待ち時間より長く保留する。現在のFR呼出しは明示タイムアウトを渡さず、WebClientExの既定値は100秒なので、ランナーの上限はこれより長く取る。HTTPエラー、空応答、JSON不正は必要に応じて別の障害種別として試す。
- シナリオ管理口はテストネットワーク内に限定する。台帳に **受信要求数・処理件数・応答結果を別々に** 残す。端末、時刻、合成請求番号、元取引番号、処理種別を関連付け、認証ヘッダーやカード情報を記録しない。重複を抑止する台帳設定でも要求数は隠さない。クライアントの同時送信防止と外部側の重複排除は個別に検証する。
- **第1優先 — 009／032**。先行端末の要求をスタブが受信した時点で応答を保留し、別プロセスの操作を開始。要求・DB状態・画面結果を記録したうえで先行応答を解放する。009の合格条件は同一請求の決済API到達が最大1件。032の結果不明記録後の再取消は0件。
- **第2優先 — 004／014／020**。受付後の切断／タイムアウトを注入し、照会成功と照会不能を分ける。再起動した別セッションから再操作し、管理者復旧前の要求数・DB更新・後続請求の継続を確認する。
- **第3優先 — 003／012**。決済成功後にDB障害を注入して部分反映と再送を確認する。正常取消では履歴2件と入金削除を確認し、取消成功後のDB障害は観測を保存する。具体復旧方式の025は仕様承認まで判定を保留する。
- 残りの正常・境界・権限を実行する。実行ごとに既存形式の `docs/test-results/YYYY-MM-DD-run-NNN.md` を追加する。前後DB状態・リクエスト数・必要な画面証跡を合成IDで記録し、実行環境・Git SHA・使用したシナリオを残す。計画作成時点では環境構築、シード投入、決済API呼び出し、テスト実行を行っていない。
